# security-audit-sdk-node Specification

## Purpose
Defines the observable behavior, Service Provider Interface (SPI) implementations, runtime isolation guarantees, and package boundaries of `@bloodtrail/security-audit-sdk-node`, the provisional first-party Node.js binding for the Bloodtrail Security Audit Core SDK.

## Requirements

### Requirement: Node platform provider implements Core platform SPIs

The `@bloodtrail/security-audit-sdk-node` package SHALL implement all platform capability SPIs defined by `@bloodtrail/security-audit-sdk-core` — identifiers (`AuditIdentifierProvider`), clock (`AuditClock`), byte length (`AuditByteLengthProvider`), timers (`AuditTimerProvider`), and schema runtime (`AuditSchemaRuntime`) — using Node.js built-in modules without third-party dependencies.

#### Scenario: Node identifiers generate cryptographically random UUIDs
- **WHEN** any identifier method (`eventId`, `operationId`, `correlationId`, `causationId`, `requestId`, `messageId`, `transactionId`) is invoked on the Node identifier provider
- **THEN** it returns a valid RFC 4122 v4 UUID string generated by `node:crypto.randomUUID()`

#### Scenario: Node clock returns current system time
- **WHEN** `now()` is invoked on the Node clock provider
- **THEN** it returns a `Date` object representing the current host system time

#### Scenario: Node byte length measures UTF-8 string byte count
- **WHEN** `byteLength(value)` is invoked on the Node byte length provider
- **THEN** it returns the exact byte length computed by `Buffer.byteLength(value, "utf8")`

#### Scenario: Node timers support handle unreferencing
- **WHEN** a timeout is scheduled via `setTimeout(callback, ms)` on the Node timer provider
- **THEN** the returned handle provides an `unref()` method that unreferences the underlying timer from the Node event loop

#### Scenario: Node schema runtime validates canonical event structures
- **WHEN** an event record is submitted to `validate(event)` on the Node schema runtime provider
- **THEN** it validates the event against the canonical contract schema definitions and returns a structured `AuditResult<void>` without exposing Ajv types in the public surface

### Requirement: Context provider isolates concurrent and nested asynchronous scopes

The package SHALL provide a `ContextProvider` SPI implementation based on `node:async_hooks.AsyncLocalStorage`. Ambient context SHALL be propagated across asynchronous execution chains, isolated across concurrent operations, and fully restored upon scope exit.

#### Scenario: Context is accessible within active execution scope
- **WHEN** an asynchronous operation executes within a scope established by `nodeContextProvider.run(context, fn)`
- **THEN** `nodeContextProvider.get()` returns the authoritative `AuditContextFrame` associated with that scope

#### Scenario: Concurrent asynchronous executions maintain strict isolation
- **WHEN** multiple concurrent asynchronous operations execute with distinct context frames
- **THEN** none of the operations observes, leaks, or mutates another concurrent operation's context frame

#### Scenario: Exiting nested context scope restores enclosing context
- **WHEN** a nested context execution completes and returns to the outer scope
- **THEN** `nodeContextProvider.get()` returns the enclosing outer context frame exactly as configured prior to entering the nested scope

#### Scenario: Reading context outside active scope returns undefined
- **WHEN** `nodeContextProvider.get()` is invoked outside any active context scope
- **THEN** it returns `undefined` without throwing or fabricating default context values

### Requirement: Shutdown timers do not retain host process exit

The Node timer provider SHALL adhere strictly to `shutdownTimerOwnership` semantics: handles SHALL support `unref()`, timers SHALL be cleared idempotently in a structured `finally`, and NO process signal handlers or intervals SHALL be installed by the package.

#### Scenario: Unreferenced shutdown timer permits clean process exit
- **WHEN** an SDK shutdown timeout is registered using the Node timer provider and no other work is pending
- **THEN** the host Node process exits cleanly without being retained by the pending shutdown timer

#### Scenario: Package installs no process signal handlers
- **WHEN** the Node binding is imported and initialized
- **THEN** no process signal listeners (`SIGTERM`, `SIGINT`) are registered on the host `process` object

### Requirement: Package boundaries enforce standalone topology and zero third-party dependencies

The package SHALL exist as a standalone workspace under `packages/security-audit-sdk-node` owning its own manifests and lockfiles per ADR 0009. It SHALL declare `private: true`, `license: "UNLICENSED"`, zero third-party runtime dependencies, and an explicitly provisional, unfrozen API surface.

#### Scenario: Shipped artifacts reference only approved built-ins and first-party SDK Core
- **WHEN** dependency verification inspects built artifacts of `@bloodtrail/security-audit-sdk-node`
- **THEN** all module specifiers are relative paths, approved `node:*` built-ins, or the declared first-party dependency `@bloodtrail/security-audit-sdk-core`

#### Scenario: Packed package installs and imports cleanly on supported Node versions
- **WHEN** the packed tarball of `@bloodtrail/security-audit-sdk-node` is installed in a clean environment outside any workspace root
- **THEN** it imports and initializes successfully under both Node 24.2.0 and Node 26.5.0

#### Scenario: Public API surface is explicitly marked provisional and unfrozen
- **WHEN** package documentation and `compatibility.json` are inspected
- **THEN** they declare the API surface as provisional and explicitly unfrozen pending vertical delivery evidence

### Requirement: Scope verification restricts platform coupling to approved Node capabilities and rejects production integration surfaces

Scope verification in `@bloodtrail/security-audit-sdk-node` SHALL inspect every code artifact under the package source root (`src/`) using an AST parser. It SHALL classify every module specifier and every free identifier referenced in value position against a declared platform coupling policy.

Verification SHALL admit only the approved Node built-in module specifiers (`node:async_hooks`, `node:buffer`, `node:crypto`, `node:timers`), first-party Core package specifiers (`@bloodtrail/security-audit-sdk-core`), relative specifiers, and standard language globals. Any unapproved Node built-in (such as `node:fs`, `node:http`, or `node:child_process`), third-party package specifier, undeclared host global (such as `process` or `window`), or dynamic evaluation primitive (`globalThis`, `eval`, `Function`) SHALL fail closed.

Verification SHALL also reject forbidden production integration filenames (including `transport`, `collector`, `browser`, `adapter`, `telemetry`, `queue`, `outbox`, `storage`, `siem`), third-party runtime dependencies in `package.json`, and forbidden exports. Diagnostics SHALL name the artifact and violation code, bounded in length, and verification SHALL fail closed if any artifact or directory cannot be read, or if the source inventory is empty.

#### Scenario: Approved Node capabilities pass and are reported
- **WHEN** scope verification runs against the `@bloodtrail/security-audit-sdk-node` source root as authored
- **THEN** verification passes, reporting the inspected artifacts, classified references, and zero undeclared couplings

#### Scenario: Unapproved Node built-in is rejected
- **WHEN** a source artifact references an unapproved Node built-in specifier such as `node:fs` or `node:http`
- **THEN** verification fails closed with an `undeclared-specifier` diagnostic naming the artifact and specifier

#### Scenario: Undeclared host global is rejected
- **WHEN** a source artifact references an undeclared host global identifier such as `process` or `window`
- **THEN** verification fails closed with an `undeclared-global` diagnostic naming the artifact and identifier

#### Scenario: Dynamic global evasion is rejected
- **WHEN** a source artifact references `globalThis`, `eval`, or `Function`
- **THEN** verification fails closed with an `undeclared-global` diagnostic

#### Scenario: Forbidden production integration filename is rejected
- **WHEN** an artifact whose filename contains a forbidden integration term (such as `transport.ts` or `collector.ts`) is present under `src/`
- **THEN** verification fails closed with a `forbidden production integration filename` diagnostic

#### Scenario: Forbidden export in package manifest is rejected
- **WHEN** `package.json` declares an export containing a forbidden term such as `transport` or `collector`
- **THEN** verification fails closed with a forbidden export diagnostic

#### Scenario: Third-party runtime dependency is rejected
- **WHEN** `package.json` declares a runtime dependency not matching `@bloodtrail/*`
- **THEN** verification fails closed with an invalid dependency diagnostic

#### Scenario: Unreadable artifact or empty inventory fails closed
- **WHEN** an artifact cannot be read, contains unparseable syntax, or the source inventory is empty
- **THEN** verification fails closed rather than reporting success

#### Scenario: Cross-package transport or browser code placement is rejected
- **WHEN** transport, collector, or browser implementation files are moved into `src/`
- **THEN** verification fails closed, detecting either a forbidden filename or undeclared platform specifier/global

### Requirement: Node binding exposes deterministic single-attempt delivery handoff

The Node binding SHALL provide a deterministic single-attempt delivery handoff for one canonical occurrence. A caller SHALL supply the exchange boundary, and the binding SHALL construct a bounded request descriptor and invoke that boundary exactly once for the attempt; it SHALL NOT open a socket, perform a live-network operation, schedule a retry itself, reserve queue capacity, or begin shutdown handling. The descriptor SHALL carry the occurrence's unchanged `event.id` and the caller-supplied zero-based attempt ordinal, defaulting to `0` when omitted, and the outcome SHALL expose one of `acknowledged`, `retryable`, `non_retryable`, or `protocol_error` without claiming delivery beyond a well-formed acknowledgment.

#### Scenario: Accepted response completes one stable attempt
- **WHEN** the supplied exchange boundary returns a well-formed acceptance for a canonical occurrence
- **THEN** the handoff invokes that boundary exactly once and returns `acknowledged` with the original `event.id` and the attempt ordinal used for that call

#### Scenario: Request construction is bounded and transport-free
- **WHEN** a canonical occurrence is handed off
- **THEN** the binding presents a bounded descriptor containing only the declared HTTP method, path, closed headers, and serialized occurrence body to the supplied exchange boundary without opening a live-network connection

#### Scenario: Caller-supplied attempt ordinal is carried into the wire correlation
- **WHEN** a caller invokes the handoff with an explicit zero-based attempt ordinal
- **THEN** the projected request and the result both carry that exact ordinal, the serialized occurrence's `correlation.retry_attempt` matches it, and the occurrence's `event.id` remains unchanged

#### Scenario: Out-of-bounds attempt ordinal is rejected before any exchange
- **WHEN** a caller supplies a negative, non-integer, or over-ceiling attempt ordinal
- **THEN** the handoff rejects the call before invoking the supplied exchange boundary and no request is constructed

### Requirement: Node binding classifies attempt outcomes fail closed

The Node binding SHALL classify a retryable response, timeout, or transport failure as `retryable`. It SHALL classify a permanent response as terminal `non_retryable`. It SHALL classify a malformed, ambiguous, or unparseable acknowledgment as terminal `protocol_error`, distinct from `non_retryable`, and SHALL never report that outcome as `acknowledged`. These classifications SHALL be deterministic from the supplied exchange outcome and SHALL not expose remote response bodies or connection-error details.

#### Scenario: Retryable exchange outcomes remain retryable
- **WHEN** the supplied exchange boundary reports a retryable response, timeout, or transport failure
- **THEN** the handoff returns `retryable` with the original `event.id` and attempt ordinal `0` and does not schedule another attempt

#### Scenario: Permanent response is terminal non-retryable
- **WHEN** the supplied exchange boundary reports a permanent rejection response
- **THEN** the handoff returns terminal `non_retryable` and does not report acceptance or schedule another attempt

#### Scenario: Malformed acknowledgment fails closed
- **WHEN** the supplied exchange boundary returns a response whose acknowledgment is malformed, ambiguous, or unparseable
- **THEN** the handoff returns terminal `protocol_error`, distinct from `non_retryable`, and never reports the occurrence as acknowledged

### Requirement: Single-attempt handoff preserves Node package and assurance boundaries

The single-attempt handoff module SHALL depend only on the Node binding's approved platform capabilities, relative modules, and the declared first-party Core dependency. It SHALL NOT add `node:http`, host `fetch`, third-party transport dependencies, browser transport behavior, backpressure queues, shutdown draining, collector validation, storage, production delivery infrastructure, real-user processing, durable delivery, or exactly-once claims, and SHALL NOT itself schedule a retry — bounded retry scheduling exists only as a separate composing module governed by a dedicated requirement.

#### Scenario: Handoff remains an injected, synthetic boundary
- **WHEN** package-scope verification and deterministic handoff tests inspect the Node binding
- **THEN** they find no live-network dependency or production transport integration and verify all outcome classes through supplied in-memory exchange results

### Requirement: Node binding provides bounded, jittered delivery retry scheduling

The Node binding SHALL provide a retry-scheduling module that composes a single-attempt handoff into a bounded delivery attempt sequence for one canonical occurrence. Only an outcome classified `retryable` SHALL cause another attempt to be scheduled; any other terminal outcome SHALL stop scheduling immediately. The module SHALL accept a configured maximum attempt count, SHALL NOT exceed it, and SHALL produce a terminal `exhausted` result carrying an observable attempt counter when the budget is spent without a non-retryable terminal outcome. The delay before each scheduled retry SHALL be a deterministic function of the attempt ordinal, a configured base and maximum delay, and an injected jitter source, computed without reference to real wall-clock time so it is verifiable under a fixed timer provider and jitter source. Each attempt SHALL carry the occurrence's unchanged `event.id` and an incrementing zero-based attempt ordinal.

#### Scenario: Only a retryable outcome schedules another attempt
- **WHEN** the wrapped handoff returns a non-retryable terminal outcome (`acknowledged`, `non_retryable`, or `protocol_error`) at any attempt
- **THEN** retry scheduling stops immediately, returns that terminal outcome, and never schedules a further attempt

#### Scenario: Retry budget is bounded and exhaustion is observable
- **WHEN** the wrapped handoff returns `retryable` for every attempt up to the configured maximum
- **THEN** retry scheduling makes no more than the configured maximum number of attempts and returns a terminal `exhausted` result carrying the number of attempts made

#### Scenario: Delay computation is deterministic and bounded
- **WHEN** retry scheduling computes the delay before a retry attempt
- **THEN** the delay is a capped exponential function of the attempt ordinal scaled by the injected jitter source's value, never exceeds the configured maximum delay, and is reproducible under a fixed timer provider and jitter source without waiting real wall-clock time

#### Scenario: Retried attempts preserve identity and advance wire correlation
- **WHEN** retry scheduling retries an occurrence through the wrapped handoff after a retryable outcome
- **THEN** every attempt carries the occurrence's identical `event.id` and an incrementing zero-based attempt ordinal consistent with the delivery conformance contract's attempt-identity requirement

### Requirement: Node binding provides bounded delivery admission backpressure

The Node binding SHALL provide a backpressure module that gates admission to an injected asynchronous delivery operation by an explicit, bounded in-flight capacity, independent of what that operation is. An admission attempted while the current in-flight count is at the configured capacity SHALL be rejected immediately and synchronously with a `rejected_overload` outcome; it SHALL NOT wait, queue the attempt for later admission, or silently drop it. Capacity consumed by an admitted operation SHALL be released exactly once when that operation settles, whether it resolves or rejects, with no drift between admitted and released counts.

#### Scenario: Admission at capacity rejects with a counted overload
- **WHEN** an admission is attempted while the in-flight count equals the configured capacity
- **THEN** the module immediately returns a `rejected_overload` outcome without invoking the wrapped operation, and an observable overload counter increments

#### Scenario: Capacity is released after completion without drift
- **WHEN** an admitted operation settles, whether by resolving or rejecting
- **THEN** the in-flight count decreases by exactly one and a subsequent admission up to the configured capacity succeeds

#### Scenario: Concurrent admission never exceeds capacity
- **WHEN** more admissions than the configured capacity are attempted with none yet settled
- **THEN** exactly the configured capacity of admissions proceed to invoke the wrapped operation and every admission beyond that is rejected with `rejected_overload`

#### Scenario: Admitted work is never silently dropped
- **WHEN** an operation is admitted
- **THEN** the module always awaits and reports that operation's own settlement and never abandons or discards it before it settles

#### Scenario: Observability exposes counters without event content
- **WHEN** an admission or rejection is observed through the module's optional observability hooks
- **THEN** the hook receives only numeric depth and capacity values and never the admitted occurrence or any operation result content

### Requirement: Node binding provides deadline-bounded delivery shutdown

The Node binding SHALL provide a shutdown module that gates admission to an injected asynchronous delivery operation with a lifecycle boundary, independent of what that operation is. Once shutdown has been initiated, every subsequent admission attempt SHALL be rejected immediately and synchronously with a `rejected_shutting_down` outcome, without invoking the wrapped operation, and with no window in which a concurrent admission attempt could be accepted after that boundary. Shutdown SHALL drain every operation admitted before the boundary against a configured deadline and SHALL return an exact accounting of how many operations were accepted, completed before the deadline, and abandoned at deadline expiry. An operation still outstanding when the deadline expires SHALL be counted as abandoned and SHALL never be reported delivered. Shutdown SHALL be idempotent: a repeated shutdown call SHALL return the same accounting without re-draining or double-counting.

#### Scenario: New admission after shutdown is rejected deterministically
- **WHEN** an admission is attempted after shutdown has been initiated
- **THEN** the module immediately returns `rejected_shutting_down` without invoking the wrapped operation

#### Scenario: Concurrent admission cannot cross the shutdown boundary
- **WHEN** shutdown is initiated concurrently with an admission attempt
- **THEN** the admission boundary applies without a gap, so no admission attempted at or after the moment shutdown is initiated is ever accepted

#### Scenario: An empty or fully drained set of operations completes before the deadline
- **WHEN** shutdown is initiated with no admitted operations outstanding, or all admitted operations have already settled
- **THEN** shutdown resolves without waiting for the configured deadline and reports zero abandoned operations

#### Scenario: Deadline expiry marks outstanding work as abandoned with exact accounting
- **WHEN** shutdown's configured deadline expires while operations admitted before the boundary remain outstanding
- **THEN** shutdown returns the exact count of accepted, completed, and abandoned operations, and no abandoned operation is ever reported delivered

#### Scenario: Repeated shutdown is idempotent
- **WHEN** shutdown is called more than once, sequentially or concurrently
- **THEN** every call returns the identical accounting from the first shutdown, and no operation is drained or counted more than once
