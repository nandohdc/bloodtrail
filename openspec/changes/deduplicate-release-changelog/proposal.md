## Why

`CHANGELOG.md` generated by Release Please contains duplicate entries for every pull request merged with standard GitHub merge commits (#471). In `v0.18.0`, Release Please generated 17 duplicate entry pairs across Breaking Changes, Added, Fixed, and Documentation sections.

The root cause is structural to how GitHub merge commits interact with Release Please's commit parser (`src/commit.ts`):
1. GitHub merge commits carry subject `Merge pull request #<num> from <branch>` and body containing the PR title (which follows Conventional Commits format, e.g. `feat(client-evidence): define ClientEvidenceEnvelope v1 schema...`).
2. Release Please's `splitMessages` splits each commit message on `\n\n(?=(?:feat|fix|docs|...): )`. This splits the merge commit into its header (ignored) and its body (parsed as a Conventional Commit pointing to the merge commit's SHA).
3. Release Please also traverses and parses the branch's individual commits, extracting the exact same Conventional Commit subject pointing to the branch commit's SHA.
4. Consequently, Release Please records two changelog lines for the exact same logical change: one linking to the merge commit SHA, and one linking to the branch commit SHA.

Upstream Release Please maintainers closed Issue #2476 stating they do not support merge commit deduplication natively and recommend squash commits instead. However, Bloodtrail's ratified release and governance specifications mandate merge commits (`gh pr merge --admin --merge`) to preserve commit history, provenance, and auditability. Upstream GitHub Repository API rejects setting `merge_commit_message: "BLANK"` with HTTP 422 `invalid_merge_commit_setting_combo`.

Therefore, the repository requires an automated, deterministic post-processing cleaner that deduplicates release changelog entries before or as part of release PR generation, preserving genuine multi-commit contributions and distinct commits while dropping redundant merge commit entries.

## What Changes

- **Add `.github/scripts/clean-release-changelog.mjs`**:
  - Parses release sections in `CHANGELOG.md` or arbitrary release notes markdown.
  - Inspects commit SHAs associated with entries within each section.
  - Queries git commit topology to identify merge commits (`parentCount > 1` with a `Merge ` subject).
  - When an entry with a merge commit SHA duplicates the subject of a branch commit in the same section, drops the merge commit entry and retains the branch commit entry.
  - Preserves intermediate commits in multi-commit pull requests (each distinct subject is kept).
  - Preserves genuine duplicate commits that share an identical subject when neither is a merge commit.
  - Provides a `--check` mode that exits with code 1 if uncleaned duplicates exist.
- **Add unit test suite `.github/scripts/clean-release-changelog.test.mjs`**:
  - Tests deduplication across all scenarios using Node's built-in `node:test`.
  - Verifies drop of duplicate merge commit entries, retention of branch commits, multi-commit PR preservation, genuine non-merge duplicate preservation, unparseable entry resilience, and `--check` mode diagnostics.
- **Update `.github/workflows/release-please.yml`**:
  - Adds a step after Release Please executes to run `clean-release-changelog.mjs` on the release PR branch `release-please--branches--main` and update the release PR description.
- **Clean existing `CHANGELOG.md`**:
  - Removes the 17 duplicate merge-commit entries from `[0.18.0]`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `release-versioning-tag-model`: Adds requirement `The generated release changelog lists each merged change once`, specifying that release changelog sections must not duplicate entries for the same change, merge commit duplicates are removed while branch commits are preserved, multi-commit PR entries are retained, and a check mode asserts cleanliness.

## Impact

- **Affected code**: `.github/scripts/clean-release-changelog.mjs`, `.github/scripts/clean-release-changelog.test.mjs`, `.github/workflows/release-please.yml`, `CHANGELOG.md`, and OpenSpec specifications.
- **Non-affected code**: Runtime SDK packages (`packages/*`), contracts (`contracts/*`), and research harness (`research/*`) are untouched.
- **Governance impact**: Touches `governance_core` paths (`.github/scripts/`, `.github/workflows/`), requiring full design-pattern assessment with complete 15-dimension security justification.
