# Finding — Hermes `allowed-tools` and the governance checker

Discharges task 7.8, which required inspecting the **actual** generated Hermes skill frontmatter
rather than assuming `Bash(openspec:*)` permits the Node checker. R22 makes that assumption itself a
failure, so this records what inspection found.

## What was inspected

| Artifact | Value |
| --- | --- |
| OpenSpec CLI | 1.8.0 (`/opt/homebrew/bin/openspec`) |
| Generated skill directories | `.hermes/skills/`, `.claude/skills/`, `.agents/skills/` |
| Frontmatter field, every skill | `allowed-tools: Bash(openspec:*)` |
| Emitting constant | `OPENSPEC_CLI_ALLOWED_TOOLS` in `dist/core/shared/allowed-tools.js` |
| Consumers | `dist/core/shared/skill-generation.js:88`, `dist/core/command-generation/adapters/claude.js:23` |

## What the field actually means

The generator's own source documents the semantics, and they are the opposite of what the task
assumed:

> Scoped to the OpenSpec CLI so agents that honor it stop prompting on each `openspec` call; the
> field **only pre-approves — it does not restrict** — so any other tool a skill or command needs
> (Read, Write, arbitrary Bash for builds/tests) stays available under the user's normal permission
> settings. Tools that don't recognize the field ignore it.

So `Bash(openspec:*)` does not block `node openspec/scripts/check-design-pattern-governance.mjs`. The
command runs; it is simply not pre-approved, so an agent that honours the field prompts before
running it, exactly as it would for any other Bash command.

## Why no expansion was made

R22 asks for "the minimum valid permission expansion". There is none available through any
repository-supported mechanism:

1. **The value is a hardcoded constant**, not configuration. `openspec config list` exposes
   `featureFlags`, `profile`, `delivery`, `telemetry`, and `workflows` — no allowed-tools key.
   `openspec config get allowedTools` returns nothing.
2. **`openspec update` accepts only `--force`.** It offers no way to supply additional tools.
3. **The generated directories must not be hand-edited.** `CLAUDE.md` states they are per-tool copies
   regenerated by the CLI. An edit would be silently reverted by the next `openspec update`, which is
   worse than no edit: it would look like an expansion existed while the guarantee had already lapsed.
4. **No expansion is needed for correctness.** Because the field pre-approves rather than restricts,
   the absence of an entry costs a permission prompt, not the ability to run the checker.

Modifying the CLI package, or vendoring a patched copy of it, would be a change to a tool outside
this repository and outside this change's authorization.

## Consequence for the governance perimeter

None. Hermes is convenience and early feedback only. The authoritative enforcement point is the
required `design-pattern-governance` CI job, which runs the checker directly and does not consult
`allowed-tools` at all. An actor who never runs the Hermes check, or whose agent ignores the field
entirely, is governed identically — which is what R11's actor-neutrality requires.

## What is tested

`openspec/tests/design-pattern-governance/hermes-integration.test.mjs` asserts, and therefore fails
on drift:

- generated skills exist to inspect, so the suite cannot pass vacuously;
- every generated skill carries exactly `allowed-tools: Bash(openspec:*)` — a regeneration that
  changes the value fails, because this repository would then be relying on a value it has not
  evaluated;
- no generated skill loses the field;
- the exact checker command appears in `docs/design-pattern-governance.md` and `CONTRIBUTING.md`;
- the policy states that an agent check is not a substitute for required CI;
- the governance CI job exists and runs the checker;
- every generated skill directory is recorded as a non-authoritative source and is not an
  actor-neutral policy document.

## Task status

Task 7.8 is **discharged by inspection with this finding**, not by making an expansion. Task 7.9 is
satisfied by the drift tests above. The premise task 7.8 was written against — that `Bash(openspec:*)`
might block the checker — turned out to be false, and recording that is the honest outcome rather
than manufacturing an expansion to tick the box.
