# ADR-SDK-009: Package and contract compatibility

- Status: Accepted for SDK-core implementation
- Date: 2026-07-31

## Decision

SDK package versions use `EXACT_ONE`: each package version supports exactly one canonical Security Audit Event Contract version across one indivisible compatibility surface comprising `compatibility.json`, generated public types, the generated validator projection, the construction-time contract-version check, and event-validation semantics. The relation is many-to-one: several SDK package versions may support the same canonical contract version, but one SDK package version does not support several canonical contract versions. Candidate `0.2.0` supports only contract `1.1.0`, bound to normative target `ee430bc6a7ca52671b294e8c73f0e2ea3ace67bf`; it rejects the prior `1.0.0` construction literal before readiness.

Exact-version instance binding is a construction invariant. A producer SDK instance can become ready only for the contract version supported by its package version; every other version fails before readiness. The SDK does not negotiate, coerce, downgrade, fall back, apply a best-effort interpretation, or switch versions after construction.

Package patch releases may fix behavior without changing canonical interpretation; additive optional API/error additions use minor versions; removals, error-meaning changes, export changes, or public/generated API incompatibility require a major version. Replacing the package's sole supported-contract baseline is SDK compatibility-major even when the canonical contract change is additive and contract-minor; generated type incompatibility is an additional trigger when it occurs, not the universal rationale. While the package remains private and unpublished in `0.x` initial development, any separately authorized release expresses that major classification through the project's `0.x` policy rather than forcing `1.0.0`; the first published release inherits the classification, and from `1.0.0` onward baseline replacement requires an SDK major. This classification does not authorize a release or version change. Deprecation is documented in a minor and removal normally waits for a major. Any authority, privacy, lifecycle, outcome, requiredness, registry, or canonical semantic change first requires a separate versioned `security-audit-event-contract` governance change.

A separately authorized collector MAY support an explicitly enumerated finite set of canonical contract versions for migration. That set does not broaden any producer package's exact-one support or any producer instance's exact-version binding. This decision creates no collector, transport, storage, production integration, publication, or real-user processing authority. `EXPLICIT_SET` may be reconsidered only when both a second canonical contract version and an authorized collector exist; either condition alone is insufficient.

SDK migration documentation remains distinct from contract/schema migration. The human adaptation policy is `MIGRATION.md`. Generated drift is a failure rather than a migration path. Compatibility fixtures pin the exact interpretation declared by their candidate manifest; the current fixture pins `1.1.0`. Consumers must check the exact manifest for each future SDK version rather than infer compatibility from package version alone. This ADR grants no package release, application integration, or production authorization.
