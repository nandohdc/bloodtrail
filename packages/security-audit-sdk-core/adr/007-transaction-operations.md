# ADR-SDK-007: Transaction-aware operations

- Status: Accepted for SDK-core implementation
- Date: 2026-07-31

## Decision

An operation handle is opaque at the public named-method boundary. Each SDK instance owns a private weak identity map that binds the exact issued handle to immutable operation, transaction, correlation, and allowed-event identity plus private monotonic state. `started` may become `committed`, `not_committed`, or `partially_committed`; `committed` may become `compensated`. Only sanctioned handle methods mutate that private state. Snapshots are immutable observational `GeneratedOperationContext` values and never carry authority back into named construction. Plain, copied, spread, cloned, serialized, modified, fake, and foreign-instance values are rejected before sink invocation.

Success that requires committed state is rejected before sink invocation until a trusted application boundary marks commit. A private event binding cannot be removed or reassigned through caller data. Authorization decision and business outcome remain distinct. Re-execution creates a new event ID linked to original identity; pure redelivery preserves the immutable event ID. Asynchronous completion requires cataloged causation. Generic complete-event APIs remain a trusted-producer boundary and do not prove application truthfulness.

The handle does not introspect databases and provides no outbox, atomicity, retry, or delivery claim.

## F-11 complete-event redelivery decision

Public `emit(event)` and `redeliver(event)` remain complete-canonical-event trusted-producer boundaries with distinct internal `generic_emit` and `pure_redelivery` intents. Pure redelivery revalidates each complete `SecurityAuditEvent`, preserves identity, canonical timestamps, schema, delivery class, correlation/causation, retry, operation/transaction, and all other metadata, and invokes the sink once per valid explicit call. It neither mutates/freezes the caller's object nor invokes identity/time generation, transformations, generated-ID history, or terminal-completion mutation.

A named method with `redelivery.event` selects `named_redelivery`, replaces the former unchecked early return with complete canonical validation, enforces fixed catalog/schema metadata, and requires operation/transaction/correlation equality with an exact supplied handle's private snapshot. F-01 same-instance authority remains a property of operation handles only. Named redelivery returns before F-02 reservation/completion. Named retry/re-execution selects `named_execution`, creates a new event ID, retains required causality, exact operation authority, and terminal semantics, and runs valid configured transformations.

A same-instance event brand and `SDK_INVALID_REDELIVERY` are rejected. They would narrow the established public complete-event signature around provenance this process cannot prove, add retained or public compatibility surface, and still establish no durable delivery. The SDK keeps no event-provenance or delivered-event ledger and cannot prove prior durable delivery, broker provenance, same-process/same-instance origin, exactly-once or at-least-once delivery, durable deduplication, or durable sink acceptance. Contract `1.0.0`, public signatures/exports, package version `0.1.0`, runtime dependencies, and production/publication restrictions remain unchanged; named-redelivery binding is a behavioral security/lifecycle tightening in a private unpublished candidate.

## F-02 concurrency pattern assessment

The architectural forces are single-threaded JavaScript interleaving across an asynchronous sink boundary, same-instance operation authority, bounded secret-free failures, explicit caller-controlled retry, zero runtime dependencies, and the future F-08 requirement to bound retained identity state. The required invariant is a synchronous `idle -> reserved` transition for one SDK-issued operation/event completion key before sink handoff can yield. Only the reserving call may validate and invoke the sink; `reserved` and `completed` both reject a competing terminal-success call with the existing `SDK_DUPLICATE_SUCCESS` result. Sink acceptance promotes `reserved -> completed`. Rejected, unknown, synchronously thrown, or rejected-promise outcomes release `reserved -> idle` in structured cleanup so a later explicit retry can acquire it. Different operation IDs and SDK instances remain independent.

Atomic reservation is selected as the controlling pattern. The implementation uses the existing exact-handle weak authority record and a finite catalog-event completion map with only `reserved` and `completed` entries; absence represents `idle`. This is also a narrowly scoped state machine and an application of an idempotency key, but neither label requires a general framework. Authority comes only from F-01 same-instance issued handle identity, and event identity comes from the cataloged named method. Reservation is established before the sink is called, so synchronous sink reentrancy observes `reserved` and cannot emit or deadlock. Accepted completion remains protected for the legitimate handle's lifetime; unrelated identifier-window churn cannot expire authority or completion state.

Single flight is rejected because callers do not share the first result: the loser must receive an immediate bounded duplicate result, and retaining or coordinating a shared promise adds failure and cancellation coupling. A process-wide lock, promise queue, polling loop, or third-party concurrency abstraction is rejected as broader than the per-instance operation model and unnecessary in JavaScript's synchronous execution segments. Treating sink acceptance as a durable idempotency guarantee is rejected because the sink result is only process-local acceptance evidence. Reserving permanently after a failed sink attempt is rejected because it would block the documented explicit retry despite no acceptance.

F-08 bounds primitive generated-event and issued-operation collision histories with deterministic insertion-order FIFO windows while keeping reservations and completions in the weak handle record. This separates active/handle-owned correctness from evictable historical collision knowledge. Window membership never grants authority; reads do not refresh age; duplicate insertion does not reorder; and the oldest historical value is evicted at capacity. Finalizers, timers, global registries, generalized caches, runtime dependencies, and durable storage are unnecessary. Tests use deferred promises and explicit barriers, not scheduling delays, to prove one reservation, one sink invocation, bounded loser diagnostics, accepted finalization, release after every non-accepted or thrown outcome, later retry, independent keys and instances, same-sink reentrancy, shutdown overlap, live-handle preservation after churn, and deterministic FIFO bounds.
